The application core runs these lessons. The network-core board target is not appropriate here. No ADC or BLE application has been added.

## The three actions

```text
BUILD on Mac:       C source + SDK → firmware file
FLASH Mac → board:  firmware file → board's flash memory
RUN on board:      power on/reset → firmware executes
```

The serial monitor only shows output. It does not start the firmware. Each lesson runs once after boot; opening the monitor afterward can miss its output, so press RESET.

Firmware persists on the board after power is removed. Only one of these lesson applications is selected at a time on the board, even though all three remain on the Mac.

## One-command helper

Run commands from the repository root. For example:

```sh
./lesson.sh build 2
./lesson.sh flash 2
./lesson.sh ports
./lesson.sh monitor /dev/cu.usbmodem0010500464391
```

`flash` builds first and stops if building fails. The helper always selects `nrf5340dk_nrf5340_cpuapp`. Each lesson uses its own `lessons/<name>/build/` folder. The helper's `-p auto` can recreate that lesson's generated build files if an incompatible board or application was cached; it does not change source code.

The helper is tailored to this Mac's installed SDK. For a relocated installation, set `WINGS_NCS_DIR` and `WINGS_TOOLCHAIN_DIR` to the appropriate SDK root and toolchain-bundle root before invoking it. Changing SDK releases requires rechecking APIs and Kconfig; changing paths alone does not validate compatibility.

Building is read-only with respect to the board. `flash` programs whichever target the selected J-Link is connected to. Use the onboard DK for these lessons; external debug-out wiring can redirect the probe to another board.

## Why were there so many export commands?

An `export` supplies a setting to commands started by the current shell. It does not install anything. A new shell generally needs setup again; `lesson.sh` performs that setup automatically for each invocation, without changing your parent terminal's environment.

| Setting used by the helper | Purpose |
| --- | --- |
| `PATH` | Find the bundled west, CMake, compiler support tools |
| `ZEPHYR_BASE` | Locate Zephyr in NCS 2.4.0 |
| `ZEPHYR_TOOLCHAIN_VARIANT=zephyr` | Select the Zephyr compiler toolchain type |
| `ZEPHYR_SDK_INSTALL_DIR` | Locate the compiler toolchain |
| `CCACHE_DIR` | Keep compiler-cache files under this project |
| CMake `USER_CACHE_DIR` | Keep Zephyr's capability cache under this project |
| CMake `NCS_TOOLCHAIN_VERSION=NONE` | Use the toolchain explicitly selected by the environment |

The first build also specifies the board and source directory. CMake records those choices in the selected build's `CMakeCache.txt`. That explains why subsequent `west build -d ...` commands can be shorter. The helper keeps the details explicit so you do not accidentally build for nRF52840 again.

## Using the Nordic VS Code UI

The workspace's `.vscode/settings.json` registers the four lesson application folders. Open this `cryptocell` folder in VS Code and use the nRF Connect sidebar. Reload the window if the old application list remains visible.

1. Select the lesson application, such as `lessons/02_sha256`.
2. Use its existing `build` configuration generated by the helper. If it is not shown, open that lesson as an existing application and add a build configuration.
3. Select **SDK 2.4.0**, the matching installed toolchain, and board **`nrf5340dk_nrf5340_cpuapp`**.
4. Keep the build directory inside that lesson: `lessons/02_sha256/build`, for example. Use that lesson's `prj.conf`; no overlay or sysbuild configuration is needed for this setup.
5. Build, then Flash the selected lesson. Check the active application before clicking Flash.
6. Open a serial terminal at 115200 baud and press RESET.

UI labels can change between extension versions. The underlying choices above must match. The documented Nordic [build-configuration workflow](https://docs.nordicsemi.com/r/bundle/nrf-connect-vscode/page/guides/build_config.html/how-to-set-up-a-build-configuration) explains selecting a board and creating a build configuration.

Choosing a UI does not change the firmware or repair J-Link compatibility by itself. It invokes the same underlying tools.

## Files you edit and files tools generate

| File/folder | Purpose | Edit it yourself? |
| --- | --- | --- |
| `src/main.c` | Application behavior | Yes |
| `prj.conf` | Requested features and memory settings | Yes, deliberately |
| `CMakeLists.txt` | Name the project and source files | When adding/changing sources |
| `README.md` | Explanation, output, experiments | Yes, add your observations |
| `build/zephyr/.config` | Final resolved Kconfig settings | No; inspect it |
| `build/zephyr/zephyr.hex` | Firmware for flashing | No |
| `build/zephyr/zephyr.elf` | Firmware plus debugging information | No |
| `build/CMakeCache.txt` | Remembered build settings | Inspect; reconfigure through tools |
| `.cache/` | Reusable compilation/capability results | No |
| `*.log` | Captured tool output | Read it when diagnosing failures |

`build/` and cache files exist before firmware runs. They are created on the Mac during compilation. The original `build-phase*.log` files were explicitly captured during our work; their names are not required by Zephyr.

## Every configuration choice in these lessons

All symbol names below were checked in the installed NCS 2.4.0 Kconfig files.

| Setting | Meaning |
| --- | --- |
| `CONFIG_SERIAL=y` | Serial driver support |
| `CONFIG_CONSOLE=y` | Console subsystem |
| `CONFIG_UART_CONSOLE=y` | Route console output through UART |
| `CONFIG_PRINTK=y` | Enable the printing function used by the lessons |
| `CONFIG_NRF_SECURITY=y` | Nordic security integration; selects entropy support |
| `CONFIG_MBEDTLS_PSA_CRYPTO_C=y` | PSA Crypto API support |
| `CONFIG_PSA_WANT_GENERATE_RANDOM=y` | Request PSA random generation |
| `CONFIG_MAIN_STACK_SIZE=4096` | 4096-byte main-thread stack for local variables/calls |
| `CONFIG_HEAP_MEM_POOL_SIZE=4096` | 4096-byte Zephyr system heap |
| `CONFIG_MBEDTLS_ENABLE_HEAP=y` | Enable the Mbed TLS allocation buffer |
| `CONFIG_MBEDTLS_HEAP_SIZE=8192` | Set that allocation buffer to 8192 bytes |
| `CONFIG_SYS_CLOCK_TICKS_PER_SEC=1000` | Timing setting used by the installed crypto samples for their CMSIS tick assumption |
| `CONFIG_PSA_WANT_ALG_SHA_256=y` | Explicit SHA-256 request in lesson 2 |
| `CONFIG_PSA_WANT_ALG_CTR=y` | Explicit AES-CTR request in lesson 3 |
| `CONFIG_PSA_WANT_ALG_CCM=y` | Explicit AES-CCM request in lesson 4 |
| `CONFIG_PSA_CRYPTO_DRIVER_CC3XX=y` | Select CryptoCell PSA driver in lesson 4 |

The memory settings follow the installed official RNG example; they have not been optimized. SDK defaults can enable other algorithms even if a lesson does not explicitly request them. `prj.conf` is not an exhaustive list of everything in the build.

Important internal/driver settings seen in the generated configurations:

- `CONFIG_PSA_CORE_OBERON=y`: the PSA core implementation is Oberon.
- `CONFIG_CRYPTOCELL_CC312_USABLE=y`: this board/security configuration supports CC312.
- `CONFIG_HW_CC3XX=y` and `CONFIG_NRF_CC3XX_PLATFORM=y`: CryptoCell hardware/platform support.
- `CONFIG_PSA_CRYPTO_DRIVER_ALG_CTR_DRBG_CC3XX_PLATFORM=y`: platform random-generation path.
- `CONFIG_PSA_CRYPTO_DRIVER_ALG_SHA_256_OBERON=y`: software SHA-256.
- `CONFIG_PSA_CRYPTO_DRIVER_ALG_CTR_OBERON=y`: software AES-CTR.
- `CONFIG_PSA_WANT_KEY_TYPE_AES=y`: internal AES key support; not a user-settable prompt in this release.

In Lessons 1–3, the separate `CONFIG_PSA_CRYPTO_DRIVER_CC3XX` algorithm driver is not selected. Lesson 4 explicitly enables it for AES-CCM; its generated `CONFIG_PSA_CRYPTO_DRIVER_ALG_CCM_CC3XX` is enabled and software CCM is not selected. Nevertheless, random generation uses the CryptoCell platform path. Do not infer the backend of one operation from another.

Source references in the installed SDK: `nrf/samples/crypto/{rng,sha256,aes_ctr}`, `nrfxlib/nrf_security/Kconfig*`, `nrfxlib/nrf_security/src/drivers/`, `nrfxlib/crypto/Kconfig`, and `zephyr/modules/mbedtls/Kconfig.psa`.
