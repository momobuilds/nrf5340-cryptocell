# Wings security prototype — presentation notes

## A one-minute explanation

> We are learning packet security on the nRF5340 DK using Nordic's installed nRF Connect SDK 2.4.0 and the standard PSA Crypto API. We prepared three separate firmware demonstrations: secure random generation, SHA-256 hashing, and an AES-128-CTR encryption/decryption round trip. Each project builds independently and has documented expected output. The current crypto experiment uses a fixed public test key and does not authenticate packets. Our next step is authenticated encryption, followed by a serialized simulated-EMG packet and a PC receiver. This is a staged learning prototype, not a finished secure communication system.

Show the recorded device output before describing a lesson as hardware-validated. The current record confirms builds and earlier successful flash operations, but still needs complete per-lesson runtime transcripts.

## What each demonstration teaches

| Demo | What to show | What it establishes when the device check passes |
| --- | --- | --- |
| Random generation | Status zero and different 16-byte output after reset | The configured PSA random-generation path works on the device; visual differences alone do not establish randomness quality |
| SHA-256 | Two similar messages with different 32-byte hashes | Deterministic fingerprints and sensitivity to changed input; hashing is not encryption |
| AES-128-CTR | Plaintext, IV, ciphertext, recovered text, exact match | A local encryption/decryption round trip works with the same key and IV; it does not authenticate messages |

The backend is operation-specific: these builds use the CryptoCell-312 platform RNG and Oberon software for SHA-256 and AES-CTR. We do not claim that every PSA operation is hardware accelerated.

## Current implemented encryption demonstration

```text
Text in nRF5340 memory
        ↓
PSA AES-128-CTR + public test key + random IV
        ↓
IV and ciphertext in nRF5340 memory
        ↓
PSA decryption on the same nRF5340
        ↓
Compare recovered bytes with the original
        ↓
Print results over the DK's serial console
```

The PC currently displays text. It does not receive a defined encrypted frame or decrypt anything. The console deliberately prints plaintext for education.

## Intended future Wings pipeline — not yet implemented

```text
EMG/ADC data (simulated first)
        ↓
Optional local DSP / feature extraction
        ↓
Serialize application packet
        ↓
Authenticated encryption on nRF5340
        ↓
Transport (serial first; production transport later)
        ↓
PC receiver: authenticate and decrypt
        ↓
Parse recovered EMG samples/features
        ↓
Signal processing / storage
```

Authentication and decryption will be provided together by an AEAD API; the application must not use output from a failed authentication attempt. We have not yet selected the final Wings packet format, transport, or key architecture.

## Prototype limitations to say explicitly

- Fixed, public test key in source: no confidentiality against someone who knows it.
- AES-CTR has no authentication tag and will be replaced by AEAD for packet protection.
- Random IV generation is used for the small CTR lesson; a future AEAD nonce strategy has not been designed.
- Text payload, no actual ADC acquisition or simulated EMG packet yet.
- Serial console diagnostics, no encrypted frame format or PC decryptor yet.
- No production key provisioning, replay protection, key exchange, or protected key service.
- No demonstrated secure boot or separated TrustZone/TF-M service.
- No timing, energy, battery-life, or hardware-acceleration performance claims.

## Suggested live demonstration

1. Flash lesson 1, open serial output, press RESET, explain why generated bytes are not ciphertext.
2. Flash lesson 2, compare the two hashes, explain that a plain hash does not stop an attacker replacing both message and hash.
3. Flash lesson 3, show `Exact match: YES`, explain that reversible encryption and authentication are different properties.

Commands and exact expected outputs are in the three lesson READMEs. Rehearse on the DK before presenting. The next learning milestone is Phase 4; the first complete EMG-to-PC demonstration remains the Phase 10 objective.
